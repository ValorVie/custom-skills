# Agent 工作流指引

本文件供 Agent 理解使用者如何選擇技能、如何提出建議，以及如何接續既有工作。
使用者的比較入口是[開發流程選擇指南](DEVELOPMENT-WORKFLOW.md)，各套操作細節
放在個別指南。本文件不定義所有任務都要遵循的固定開發順序。

## 先理解目前工作，再提出建議

讀取使用者目標、專案規則、相關程式與既有工件，確認這次要交付什麼。
能從現場查到的內容先查；需要使用者決定的方向，再帶著證據、建議與理由討論。

| 目前情況 | 合適的回應方式 |
| --- | --- |
| 使用者已指定技能或流程 | 讀取並接續該方法，說明必要的相依能力或差異 |
| 使用者指向既有計畫、規格或任務 | 先讀工件與現況，從未完成部分接續 |
| 範圍明確，可以直接驗證 | 直接處理或選最小必要技能，不為形式增加完整流程 |
| 使用者要比較方法，或尚未選擇 | 參考選擇矩陣，推薦合適方法並說明理由與取捨 |
| 查不到關鍵資訊、證據矛盾，或方向與範圍需要決定 | 說明已查內容、未知與選項，討論後再處理依賴該決定的工作 |

不必每次列出所有框架。建議的深度應足以讓使用者選擇，不把單一技能的細節問題
擴大成另一輪全面設計。

## 怎麼說明選擇

對會改變工作方式的建議，交代：

- 目前需要解決的問題與已查到的證據。
- 推薦的技能或流程，以及它補足哪個缺口。
- 有實際差異的替代選項、額外產出與使用者參與程度。
- 若會影響範圍、費用或操作授權，說明影響及需要決定的事項。

日常細節可依專案慣例與適用的最佳實踐處理。使用者已確認的方向與授權，在範圍
沒有改變時應沿用；不要只為形式反覆要求確認。

## 接續與跨套組合

先辨識目前的規格、計畫與任務來源，再決定是否需要補技能。
例如使用者已有 OpenSpec change，可補來源查證或監控方法，毋須重建規格。
原流程已有審查時，額外審查應說明要補哪一類缺口。

交棒時保留已確認的目標、限制、工件位置與驗收方式；具體檢查如下：

| 檢查項目 | 處理方式 |
| --- | --- |
| 同名技能或命令 | 使用來源與完整名稱辨識，不只靠 `/plan` 或 `/review` 等短名 |
| 不同規格與任務格式 | 確認下一個入口讀得懂；不默默複製第二份規格 |
| 多個總入口或啟動腳本 | 確認本次由哪個已選流程接續，不同時讓多套方法重新規劃 |
| 不同測試或審查步驟 | 沿用本次已選方法；有衝突時說明差異，不混成互相矛盾的要求 |
| 缺少命令、代理、工具或參考文件 | 回報實際缺項與可行替代，不宣稱完整能力已可用 |

agent-skills 的部分命令有特定路徑與派工要求，混用前先看
[agent-skills 指南](agent-skills-guide.md)。需要選擇由主代理、工作代理或審查者
處理時，可使用已安裝的 `custom-agent-router`；它處理執行安排，不替使用者選定
另一套開發流程。

## 專案規則與操作界線

本文件是使用指引，不取代使用者指令或專案入口中的權限規則。

- 安裝技能不等於使用者已選擇其完整流程。現有通用入口對高階流程的呼叫限制仍適用。
- 任務狀態、認領、依賴及結案使用專案已宣告的系統；未宣告時，不因形式需要另建。
- 正式規格、任務狀態與操作證據各沿用專案指定位置，不建立互相競爭的真相來源。
- 技能提出的提交、推送、部署、資料或權限操作，仍依當前授權執行。
- 記憶提供背景，不是新授權；完成聲明應根據這次可確認的證據。

專案自己的任務映射與安全細節請讀該專案的入口文件。不要把單一專案的路徑、
帳號或操作規則寫進通用指南。

## 維護方式

本文件維護 Agent 的建議與接續方式；使用者比較維護在 `DEVELOPMENT-WORKFLOW.md`。
通用執行政策仍由 repo 根目錄 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md`、
`INSTRUCTIONS.md` 及其分發模板管理。整理指南不會自動更新已安裝專案的設定。

若另有明確工作要修改通用政策，才依專案模板流程同步與測試；不要把這份指南
整段貼進每個專案的入口文件。專案覆寫保留在受管理區塊之外。
