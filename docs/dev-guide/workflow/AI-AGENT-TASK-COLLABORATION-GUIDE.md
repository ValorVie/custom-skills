# AI Agent 任務協作指南

本指南說明如何把 Beads 任務契約、文件寫作、注意力維持與視覺說明組合成可移植的
AI Agent 協作方式。重點不是每次載入所有 Skill，而是讓每個工具只處理自己負責的問題。

## 能力分工

```text
任務目標
├─ 需要跨回合保存狀態 → 專案 tracker ＋任務契約
├─ 需要正式文件       → custom-skills-doc-writer
│                        ├─ humanizer-zh-tw：整理自然繁體中文
│                        └─ ASD-STE100 原則／檢查器：輔助英文技術文字
├─ 長任務容易失焦     → i-have-adhd
└─ 關係難以用文字說明 → show-me
```

| 能力 | 負責什麼 | 不負責什麼 |
| --- | --- | --- |
| 專案 tracker 與任務契約 | 任務狀態、範圍、依賴、驗收與認領 | 文件語氣與圖表 |
| `custom-skills-doc-writer` | 文件目的、結構、證據界線與維護位置 | 任務認領與執行授權 |
| `i-have-adhd` | 維持目前焦點、已完成內容與下一個動作 | 取代 tracker 或正式規格 |
| `show-me` | 用最小圖示說清楚流程、關係與責任邊界 | 驗證內容正確或證明系統可用 |

專案規則與使用者指令永遠優先。安裝 Skill 不代表取得修改任務系統、Git、服務、資料庫
或正式環境的權限。

## 安裝按需能力

在信任來源且專案允許執行 `npx` 的環境安裝：

```bash
npx skills add ayghri/i-have-adhd
npx skills add humanlayer/skills --skill show-me
```

安裝後依各 Agent 工具的 Skill 呼叫方式使用。不要假設 Skill 會在每輪自動啟用。

來源：

- [`ayghri/i-have-adhd`](https://github.com/ayghri/i-have-adhd)
- [`humanlayer/skills` 的 `show-me`](https://github.com/humanlayer/skills/tree/main/plugins/show-me/skills/show-me)

## 任務開始前

需要持久追蹤的工作，先使用專案已宣告的 tracker。不要另建 Markdown 任務清單或第二套
狀態來源。單次問答、唯讀查值或能在同一回合完成的小修改，通常不需要新增任務。

Agent 應先調查現有文件、程式、歷史與 tracker，再草擬任務契約。只有找不到答案、
證據互相衝突或需要使用者決定時才提問。契約至少回答：

1. 最後要交付或證明什麼？
2. 為什麼現在要做，目前有什麼證據？
3. 可以改什麼，不能改什麼？
4. 正式規格、操作指南或調查報告在哪裡？
5. 哪一項依賴真的會阻擋本任務？
6. 如何驗證成功，看到什麼情況要停止？

使用者確認契約後才開始修改。目標、範圍、授權、依賴、驗收或停止條件有實質改變時，
應停止並重新確認，不能只更新內部摘要後繼續。

## 把 Beads 任務契約移植到專案

以下做法適合已使用 Beads，而且希望 Agent 能跨回合接續工作的專案。尚未安裝或初始化
Beads 時，先依[Beads 指南](../ai-tools/BEADS-GUIDE.md)完成安裝、初始化與備份設計。本節只處理
「什麼任務可以開始」，不重複一般安裝說明。

### 先分清楚四層資訊

這套任務契約的核心改善只需要修改四份規則文件；既有 hook 已能載入內容，所以不必另外寫程式。

| 檔案 | 放什麼 | 不要放什麼 |
| --- | --- | --- |
| `.beads/PRIME.md` | 每輪都要遵守的短版開工關卡，以及完整規則的連結 | 完整欄位表、任務現況、分類清單或長篇範例 |
| `docs/agents/issue-tracker.md` | 六項契約、欄位對應、生命週期、依賴語意、操作方式與例外 | 會隨單一任務變動的進度 |
| `AGENTS.md` | 專案使用哪個 tracker、何時需要契約、安全與授權邊界 | 重複整份 tracker 操作手冊 |
| `CLAUDE.md` | 與 `AGENTS.md` 相同的專案級任務規則入口 | 只對單一工具成立、卻被誤當成專案規則的內容 |

如果專案只維護一份 Agent 指令檔，就只修改那一份。若同時維護 `AGENTS.md` 與
`CLAUDE.md`，兩者的實質專案規則要一致，但不必把各工具產生的管理區塊做成完全相同。

Beads 的 Codex 整合通常會產生技能、`AGENTS.md` 管理區塊與 `.codex/` hooks。先讓 Beads
產生這些檔案，再把專案規則放在管理區塊外；更新 Beads 後也先查看差異，避免重新執行 setup
時蓋掉專案覆寫。

```bash
bd setup codex
bd setup codex --check
```

使用 Claude Code 時，另外執行 `bd setup claude` 與 `bd setup claude --check`。不同版本的
hook 事件可能不同；以整合檢查、Agent 工具的 hook 檢視功能及實際產生的設定檔為準。
Hook 只負責載入提醒，不應自動建立、認領、關閉或修改任務。

### 完整規則寫在 `issue-tracker.md`

`docs/agents/issue-tracker.md` 是這套做法的唯一完整規則來源。至少寫清楚下列內容：

1. 哪些工作需要持久任務，哪些小工作可以直接完成。
2. 建立前如何搜尋所有狀態，避免重複任務。
3. Agent 如何調查並填入六項契約。
4. 使用者如何確認，以及 `agent-ready` 的加入和移除時機。
5. 哪些關係是真阻擋、相關、發現來源或父子範圍。
6. 如何記錄驗證證據、關閉結果與剩餘工作。
7. 哪些高風險操作仍需要另外批准。

六項契約可依下表對應 Beads 欄位。欄位名稱以目前安裝的 `bd create --help` 為準；不同版本
若沒有同名欄位，保留問題本身，再映射到最接近的正式欄位。

| 必須回答的問題 | Agent 先查什麼 | Beads 欄位 |
| --- | --- | --- |
| 最後要交付或證明什麼？ | 使用者目標、既有任務與正式計畫 | 標題與 `description` |
| 為什麼現在要做，目前有什麼證據？ | 現況、失敗紀錄、程式、報告與最近驗證 | `context` |
| 可以改什麼，不能改什麼？ | 專案規則、工作區、權限與既有批准 | `description` 與 `context` |
| 正式規格、操作手冊或調查報告在哪裡？ | 版本庫中的權威入口 | `spec_id` |
| 哪件工作真的會阻擋本任務？ | 不完成就不能安全開始或驗收的原因 | dependency |
| 如何驗證成功，看到什麼要停止？ | 測試、操作手冊、風險與回復條件 | `acceptance_criteria` |

Agent 填寫時要分清楚「已直接驗證」、「根據證據推論」與「仍未知」。使用者的角色是確認或
修正契約，不是代替 Agent 搜尋文件、程式與歷史。只有找不到資料、證據衝突，或答案需要決定
目標、範圍、授權、風險與驗收取捨時，Agent 才提出問題。

### 用 `agent-ready` 區分兩種 ready

`bd ready` 回答的是「依賴圖上是否沒有未完成的阻擋」，不能證明任務內容足以開工。
`agent-ready` 則表示 Agent 已完成事前調查、六項契約已填妥，而且使用者已明確確認。

```text
觀察或需求
  → 搜尋所有狀態的既有任務
  → 建立或重新開啟草稿
  → Agent 調查並填妥契約
  → 使用者明確確認
  → 加入 agent-ready 並認領
  → 執行、驗證、關閉
```

建立前不能只看 `bd ready`，因為它不會顯示已關閉、被延後或目前有阻擋的相似任務。至少用
結果、受影響元件及關鍵詞搜尋：

```bash
bd search "<關鍵詞>" --status all
bd search "<關鍵詞>" --status all --desc-contains "<元件或預期結果>"
```

找到相同結果時更新原任務。症狀相似但根因、修改範圍或驗收不同時，才保留獨立任務並說明
關係。搜尋結果可能受預設筆數限制；大型資料庫應縮小條件或提高 `--limit`。

新任務先維持未認領，也不加入 `agent-ready`。可先用 `--dry-run` 檢查即將寫入的內容：

```bash
bd create "[area] <可驗收結果>" \
  --type=task \
  --description="<交付內容、納入與排除範圍>" \
  --context="<目前證據、推論與未知>" \
  --spec-id="<版本庫內的正式文件>" \
  --acceptance="<驗證方式、成功與停止條件>" \
  --dry-run
```

預覽正確後移除 `--dry-run`，建立尚未認領的草稿。這一步仍不加入 `agent-ready`。

使用者明確確認後，才依序留下確認紀錄、加標籤並認領：

```bash
bd comments add <id> '<日期與已確認的契約範圍>'
bd update <id> --add-label agent-ready
bd update <id> --claim
```

Agent 自動挑工作時，只從已確認的清單選擇：

```bash
bd ready --label agent-ready
```

總關卡、里程碑或只用來彙整子任務的 epic 不加入 `agent-ready`。這個標籤也不代表資料庫寫入、
部署、服務、流量、憑證、費用或正式環境操作已獲批准；這些操作仍依專案規則逐階段確認。

### 契約改變時先停止

執行中若目標、修改範圍、授權、真阻擋、驗收方式或停止條件有實質改變，Agent 應先停止本任務
的修改，並移除標籤：

```bash
bd update <id> --remove-label agent-ready
```

接著更新契約、說明新舊差異，再交給使用者重新確認。沒有回覆不算同意，也不能用先前對另一
個範圍的批准繼續工作。

只有「前一件工作未完成就不能安全開始，或不能合法驗收」才建立阻塞依賴。其他關係分開表達：

- `relates-to`：方便找到相關工作，不影響 ready。
- `discovered-from`：保存工作從哪裡發現，不暗示執行順序。
- parent-child：表示範圍歸屬，不等於阻擋。

不要為了把不完整任務藏起來而虛構 blocker；應讓它保持未確認、沒有 `agent-ready`。

### `PRIME.md` 只放每輪需要的短提示

`.beads/PRIME.md` 會覆寫 `bd prime` 的預設工作流程文字，而且可能在工作階段開始、使用者送出
提示或上下文壓縮時重複載入。內容越長，越會占用對話空間，也越容易和完整規則不同步。

可從以下最小版本開始，再加入專案確實需要每輪提醒的 Git 或安全邊界：

```markdown
# Beads 工作脈絡

## 每輪開工關卡

- 簡單問答、唯讀查值與可直接驗證的小修改依專案規則直接處理。
- 需要持久追蹤的工作依序處理：
  1. 搜尋全部狀態，並完成必要的唯讀調查。
  2. 建立或重新開啟草稿；不認領，也不加 `agent-ready`。
  3. Agent 依 `docs/agents/issue-tracker.md` 填妥六項契約。
  4. 使用者明確確認並留下紀錄後，才加 `agent-ready`、認領並修改。
  5. 契約有實質改變時，停止、移除 `agent-ready` 並重新確認。
- `agent-ready` 不取代高風險操作的個別批准。

完整規則以 `docs/agents/issue-tracker.md` 為唯一來源。
```

不要把目前任務、分類清單、完整指令參考或 Beads 記憶複製進 PRIME。需要確認覆寫內容時執行：

```bash
bd prime --no-memories
```

### 在 Agent 指令檔只留入口與邊界

把下列短規則放在 `AGENTS.md` 與需要支援的其他 Agent 指令檔，並依專案補上實際安全界線：

```markdown
## 任務追蹤

- Beads 是本專案唯一的持久任務系統，不建立 Markdown 或其他平行任務清單。
- 需要持久追蹤的工作，Agent 先依 `docs/agents/issue-tracker.md` 查重並準備六項契約。
- 使用者確認前不得加入 `agent-ready`、認領或開始修改。
- 契約有實質改變時，停止並重新確認。
- `agent-ready` 不會擴大專案原有的修改、Git 或高風險操作權限。
```

不要把 setup 工具產生的管理區塊當成專案授權。使用者指令、專案規則與安全邊界仍優先。

### 一種資料只維護一份

| 資料 | 正式位置 |
| --- | --- |
| 任務狀態、負責人、依賴、驗收、目前備註與確認紀錄 | Beads |
| 穩定規格、設計、操作順序、停止與回復方法 | 版本控制文件 |
| 某次調查或執行取得的證據 | 日期型報告或任務留言 |
| 每輪開工提醒 | `.beads/PRIME.md` |
| 專案安全、授權與工具路由 | `AGENTS.md`、`CLAUDE.md` 等專案指令檔 |

若需要看板，優先從 Beads 產生唯讀檢視。不要再維護一份逐項複製狀態的 Markdown 看板；那會
把每次任務更新變成雙寫，最後難以判斷哪一份才是目前狀態。

### 用一個不完整任務驗證移植結果

完成設定後，不要直接用大型任務測試。先準備一個刻意缺少部分資訊的低風險範例，確認：

1. `bd setup codex --check` 或對應 Agent 的整合檢查能辨識目前狀態。
2. `bd prime --no-memories` 只顯示短版開工關卡，並連到完整規則。
3. Agent 會搜尋全部狀態，且不會把查得到的問題丟回給使用者。
4. 使用者確認前，任務未認領，也沒有 `agent-ready`。
5. 確認後才留下留言、加入標籤並認領。
6. 人為改變一項重要契約後，Agent 會停止、移除標籤並要求重新確認。
7. 驗收通過後才關閉；回合結束本身不算完成證據。

最後執行 `git diff --check`，並人工確認 setup 沒有覆蓋專案原有規則。這項演練只能證明流程已
接好，不能證明所有 Agent、模型與任務都會穩定改善；仍應觀察重複任務、錯誤認領、重新調查、
契約重開與狀態雙寫是否真的下降。

## 執行期間如何選工具

### 一般任務

直接依任務契約執行並驗證。只在出現對應問題時加入其他能力：

- 工作跨多個階段、回合或 Agent，開始忘記目前焦點時，使用 `i-have-adhd`。
- 要建立計畫、報告、指南、手冊或規範時，使用 `custom-skills-doc-writer`。
- 讀者必須同時理解三個以上元件、分支或責任邊界時，使用 `show-me`。

### 使用 `i-have-adhd`

把它當成目前工作的短期導航，不是新的任務資料庫。狀態摘要只需要保留：

- 目前唯一目標。
- 已確認的證據與已完成事項。
- 現在要做的下一個動作。
- 未知、阻擋與停止條件。

階段完成或上下文切換時更新摘要；正式狀態仍寫回 tracker，正式結論仍寫進版本控制文件。

### 撰寫正式文件

`custom-skills-doc-writer` 先依讀者任務決定文件類型、主線與證據界線。完成規則式寫作
後，再用 `humanizer-zh-tw` 整理可改寫的繁體中文。英文技術說明遵守 ASD-STE100 的
清楚表達原則；若專案另有合法標準文件與已批准檢查器，可依專案規則執行輔助檢查。

命令、路徑、URL、版本、識別字、數字、狀態與停止條件必須保留原意。語氣整理與機器
檢查都不能取代事實核對。

### 使用 `show-me`

文字已能直接回答時，不要為了裝飾增加圖。適合使用的情況包括：

- 多個元件之間的呼叫或資料流。
- 有三個以上步驟、分支或狀態變化。
- 檔案、模組或 Agent 的責任邊界。
- 修改前後的結構差異。

選擇能回答問題的最小形式：簡單流程用文字樹或偽碼，互動順序用 Mermaid，結構修改用
diff。圖放在相關說明旁邊，並刪除與目前問題無關的元件。

## 完成任務

完成時先用任務契約的驗收方式檢查結果，再更新專案 tracker。文件保存可長期使用的
結論、證據與操作入口；tracker 保存工作狀態；`i-have-adhd` 摘要在交接後可以丟棄；
`show-me` 圖只在仍能幫助讀者時保留。

```text
驗證成功
├─ 更新 tracker：完成狀態、剩餘工作與依賴
├─ 更新文件：正式結論、證據與使用方式
└─ 清理暫時摘要：不留下第二份任務狀態
```

## 常見錯誤

- 安裝所有 Skill 後，每個任務都完整套用。
- 把 `bd ready` 當成任務內容已足以交給 Agent 的證明。
- 建立任務後立刻認領，讓使用者只能事後修正範圍。
- 要求使用者自己查資料並填完六項契約。
- 把完整 tracker 手冊與目前任務狀態塞進每輪載入的 PRIME。
- 用 `i-have-adhd` 摘要取代 tracker，造成兩份狀態互相漂移。
- 用 `show-me` 圖表取代測試、來源或內容驗證。
- 把 tracker 的即時進度逐字複製到長期文件。
- 讓 Skill 覆蓋專案的安全、授權、Git 與資料規則。
