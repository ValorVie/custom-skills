# 成稿與陌生讀者檢查

先自行修正能直接判定的問題，再回報仍需要使用者決定的內容。短文件按風險縮減檢查，不為形式製造額外流程。

## 第一關：目的與主線

- 內容是否與預定讀者有關，讀者找得到、看得懂並能用來完成任務？這四項是依 ISO 24495-1 公開讀者結果整理的檢查方向，不是符合性認證。
- 標題是否說明實際主題，而不是「相關說明」或「完整報告」？
- 開頭是否直接交代目的、目前答案、決定或要完成的行動？
- 只看二級標題，能否看出問題與答案的先後順序？
- 每一節是否對應寫作小卡中的讀者問題？
- 結尾是否提供具體完成條件、未知或下一個決定，而不是通用樂觀句？

若標題像模板分類而不是讀者問題，先改標題，不用正文補救。

## 第二關：段落連貫

- 每節第一段是否直接回答該節問題？
- 代名詞、路徑、版本、元件和狀態是否有明確對象？
- 因果、依賴、比較、時間和狀態改變是否直接寫出？
- 前一節是否提供下一節需要的背景？
- 同一項內容是否在摘要、發現、建議與結論重複？
- 表格是否真的有重複欄位；若內容是在說原因或過程，改用段落是否更清楚？
- 是否有空章節、占位文字或只為模板完整而寫的內容？

## 第三關：證據與行動

- 重要事實是否能連回直接證據？
- 已驗證、推論、未知、已執行與未執行是否分清楚？
- 建議是否說明適用條件、排除理由與驗證方式？
- 計畫是否把未執行步驟誤寫成完成？
- 進度是否連回正式任務系統，而不是維護第二套狀態？
- 操作是否有目標、權限、影響、前檢、成功條件、停止點、驗證與回復？
- 內部連結能否開啟，外部引用是否直接支持相鄰主張？

## 第四關：語言、事實與技術字串

- 人物、時間、數字、指令、條件、狀態、範圍與不確定性是否和來源一致？
- code、命令、URL、路徑、API 欄位、設定鍵、識別字、產品名、log、錯誤訊息、引用與來源標題是否逐字保留？
- 英文說明文字是否固定用詞、聚焦單一主要意思，並清楚寫出動作者、動作、對象和必要條件？
- 中文是否先說結論、優先使用通行中文，並刪除不提供資訊的鋪墊？是否沒有宣稱符合 ASD-STE100？
- `humanizer-zh-tw` 是否只在規則式改寫後整理可改寫文字，而且整理後已重新比對技術字串與事實？
- 若提供了合法 PDF 與已批准的本機檢查器，是否依固定介面執行並判讀 JSON？缺任一項時是否明說未執行？
- 檢查結果是否只作提醒，沒有把「無提醒」寫成 ASD 認證、完整符合或語意正確？

## 第五關：格式與生命週期

- frontmatter 必填欄位符合專案規則。
- 檔名是正確的時點格式或穩定入口名稱。
- 路徑、`type`、`topic` 和實際用途一致。
- Markdown 表格、標題層級與 fenced code block 正確。
- 新主題、取代關係或難以瀏覽的清單已更新最近索引。
- 沒有為單一文件建立空目錄或未維護的 metadata 分類。

## 陌生讀者試讀

長篇、跨層或高風險文件才執行。測試者不能取得原對話或作者腦中的背景。

### 準備問題

從寫作小卡挑三到五題，涵蓋：

- 文件的主要答案或行動。
- 一個重要證據或理由。
- 一個限制、停止點或非目標。
- 操作文件的成功結果或回復方式。
- 文件完成後的下一個入口。

### 記錄方式

每題記錄：

| 問題 | 結果 | 引用位置 | 缺口 |
| --- | --- | --- | --- |
| ... | 答對／答錯／靠猜／找不到 | 標題或段落 | 需要補什麼 |

只有能引用文件位置而且沒有補充對話背景，才算答對。答案正確但靠外部常識或猜測，記為「靠猜」。

### 證據界線

- AI 測試稱為「AI 可理解性檢查」。
- 真人實際照文件完成工作，才能稱為「真人使用結果」。
- 試讀不能證明命令可執行、程式正確、回復有效或內容已獲批准。

發現缺口後先修文件，再重跑受影響問題；不需要每次重跑已明確不受影響的題目。

## 最後交付檢查

- 文件能獨立閱讀，不依賴聊天紀錄。
- 主要讀者能在合理位置找到答案。
- 沒有新增第二份真相或任務清單。
- 驗證結果沒有超出證據能支持的範圍。
- 技術文件的機器檢查狀態是未檢查、無提醒、有提醒或工具失敗其中之一，而且有相符證據。
- 回覆使用者時列出修改、驗證、未知與下一個入口。
