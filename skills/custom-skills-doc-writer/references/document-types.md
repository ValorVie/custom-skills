# 文件類型與最小骨架

文件類型代表讀者現在要完成的工作，不是固定文章外觀。先選最接近的主要用途，再依實際問題調整標題；沒有內容的部分不要建立。

## 快速判斷

| 讀者現在要做什麼 | 類型 |
| --- | --- |
| 規劃未來工作或提案 | `plan` |
| 查清原因、比較方案或掌握進度 | `report` |
| 整理外部證據與未知 | `research` |
| 完成一個實際目標 | `guide` |
| 安全執行會改變系統的操作 | `runbook` |
| 跟著練習學會一項能力 | `tutorial` |
| 精確查找定義、欄位、介面或限制 | `reference` |
| 理解原理、原因、關係或取捨 | `explanation` |
| 保存會議、事件、決定或變更 | `record` |
| 定義必須遵守的規則 | `standard` |

常見混淆：

- `guide` 是完成目標；`tutorial` 是學習；`reference` 是查資料；`explanation` 是理解原因。
- `report` 保存分析與結論；`record` 保存已發生的事實或已做出的決定。
- `research` 可以保留未知；`report/analysis` 應回答一個明確的比較問題。
- `runbook` 會改變系統並需要停止與回復；一般 `guide` 不一定有 mutation。

## 計畫 `plan`

### 共通骨架

1. 最後要達成什麼，目前在哪裡。
2. 為什麼現在要做，有哪些現況證據。
3. 可以改什麼，明確不做什麼。
4. 工作順序、真正依賴及每階段產出。
5. 風險、停止條件、驗收與回復方式。

計畫描述未來，不把尚未執行的步驟寫成已完成。若已有任務追蹤系統，文件只保留工作結構與任務連結，不維護另一份逐項狀態。

### `general`

用於不屬於下列特殊情境的工作。重點是目標、範圍、順序與驗收，不需要為了完整度加入技術選型表。

### `feature`

增加：使用者問題、可觀察行為、介面或資料變化、相容性與使用者驗收。不要把實作元件清單當成需求。

### `refactoring`

增加：現有痛點、必須保持不變的行為、受影響入口、重構前後的回歸證據。若同時改變業務語意，應拆成新功能或技術提案。

### `migration`

增加：來源與目標狀態、分階段轉換、雙軌期、資料與設定相容性、切換條件、每階段回復點。清楚區分已準備、已安裝、已套用與已接流量。

### `rfc`

用於尚待採納的方案。順序是待決問題 → 限制 → 提案 → 替代方案與取捨 → 影響 → 採納方式。採納後另留短決策紀錄，不把整份比較永久當成現行決定。

## 報告 `report`

### `investigation`

回答「發生什麼、為什麼、影響到哪裡」。

1. 問題、觸發事件與範圍。
2. 調查方法與證據界線。
3. 依證據排列的發現。
4. 根因、促成因素與影響。
5. 已排除項目、未知與下一個決定。

症狀、根因和相關但非根因的問題要分開。沒有直接證據時使用「推論」而不是肯定語氣。

### `analysis`

回答「在明確限制下，哪個選擇較合適」。

1. 決策問題與評估條件。
2. 現況與不可改變的限制。
3. 各方案用相同欄位比較。
4. 建議、理由與不採用其他方案的原因。
5. 風險、未知與驗證方式。

只有方案真的共享比較欄位時才使用表格；論證放在表格後的段落。

### `status`

回答「最後要去哪裡、現在在哪裡、下一步是什麼」。

1. 最終目標與本期位置。
2. 本期已直接驗證的結果。
3. 真正阻擋與其證據。
4. 下一步、負責人、人工停止點與正式任務連結。

不複製任務系統的逐項狀態，也不把「已準備」寫成「已完成」。

## 研究 `research`

研究用來整理尚無定論的外部證據。

1. 研究問題、範圍與排除項目。
2. 搜尋方法、資料日期與來源可信度。
3. 證據分組，以及每項能證明和不能證明什麼。
4. 目前可支持的結論。
5. 證據不足、互相衝突處與下一個查證點。

區分實證研究、正式標準、成熟方法、供應商說法與個人意見。不要用安裝數、星數或搜尋排名代替品質證據。

## 操作指南 `guide`

指南幫讀者完成一個具體目標。

1. 適用情境、完成結果與前置條件。
2. 依實際執行順序排列的步驟。
3. 每個關鍵步驟的可見結果。
4. 完成驗證。
5. 常見失敗、恢復方式與相關參考資料。

背景只保留執行所需的量。精確欄位放參考資料，深入原因放原理解釋。

## 維運手冊 `runbook`

維運手冊用於可重複、可能高風險或需要稽核的操作。

1. 目標、目前狀態、操作階段與本次停止點。
2. 目標系統、執行身分、權限、影響與明確非目標。
3. 前置檢查、備份與預覽。
4. 完整套用步驟；高風險操作分成可獨立批准的階段。
5. 每階段成功條件與立即停止條件。
6. 最終驗證、稽核紀錄與回復方式。
7. 成功後回到哪個章節繼續。

詳細欄位使用 [content-blocks.md](content-blocks.md) 的「安全操作」。不能驗證回復前提時，不把文件標成可用的正式 runbook。

## 教學 `tutorial`

教學讓學習者透過一條可成功完成的路徑取得能力。

1. 學習者起點、需要的工具與可見成果。
2. 先做第一個最小成功結果。
3. 每次加入一個新概念並立刻使用。
4. 每一步說明應看到的結果與常見偏差。
5. 回顧學到什麼，以及下一個可獨立完成的練習。

不要先講完所有背景才讓讀者動手。分支、完整參數表和深入原理連到指南、參考資料或原理解釋。

## 參考資料 `reference`

參考資料讓讀者快速且精確地查到事實。

1. 被查找的系統、介面或資料範圍。
2. 名詞、欄位、參數、回傳值、限制與預設值。
3. 精確且最小的範例。
4. 錯誤、版本差異與相容性。
5. 相關操作指南和原理解釋。

結構應穩定、可掃描。不要混入長篇教學或未證實的建議。

## 原理解釋 `explanation`

原理解釋幫助讀者建立正確心智模型。

1. 想理解的問題或容易誤解的現象。
2. 必要背景與元件關係。
3. 原理、原因、取捨或限制。
4. 具體例子與反例。
5. 相關操作和參考資料。

原理解釋不應假裝成操作步驟。若讀者要立刻完成工作，另寫或連到指南。

## 紀錄 `record`

### `meeting`

保留日期、參與者、實際議題、決議及行動的正式任務連結。沒有討論、決議或行動的分類直接省略。

### `incident`

順序是影響與偵測 → 時間線與處理 → 根因和促成因素 → 恢復驗證 → 有負責人、優先級、追蹤編號與完成條件的改善措施。改善措施的狀態留在任務系統。

### `decision`

只保留狀態、問題背景、決定、理由、後果和取代關係。只有真的評估過替代方案才列出，不把決策紀錄寫回完整 RFC。

### `changelog`

依版本或日期保存實際變更、相容性影響、升級注意事項與相關連結。不要加入沒有發生的「未來規劃」。

## 規範 `standard`

1. 目的、適用範圍和不適用情況。
2. 名詞，以及「必須、建議、可以」等規則強度。
3. 規則與各自理由。
4. 例外、批准方式與期限。
5. 自動或人工檢查方式。
6. 版本、負責人、審閱週期與取代關係。

規範應能判定符合或不符合。只有價值宣言、沒有檢查方式的內容不算可執行規範。
